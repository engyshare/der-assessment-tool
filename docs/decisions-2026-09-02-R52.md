## §2 계산 검증 — **대조군은 없다. 대신 「단계별로 검증 가능한 보고서」를 만든다**

> *「계산값 대조는 현 시점에서 불가함 (처음 하는 사업이라서 계산 결과가 없음) 대신
> 본 프로그램에서 순차적으로 검증을 진행할 수 있도록 단계적으로 정보를 제공해야 함.
> 예를 들어 검증 보고서를 별도로 생성하고, 각 단계별로 전제한 수치, 이를 통해 계산된
> 수치, 그 다음 단계에 계산된 수치, 계산 수식 등을 구체적으로 검증 가능한 형태로
> 제공해야 함」*

### 이것이 뜻하는 것 — ★★ **`status-human.md` 2단계를 닫고 새 산출물을 연다**

  하는 사업이라서 계산 결과가 없음」*. ⚠ **「미해결」이 아니라 「대조군이 존재하지
  않는다」**이며, 그 사실이 정직한 상태다. 대장의 `oracle.prior_demo_assumptions`·

  문면을 이 판정으로 갱신한다** — 「회신 대기」가 아니라 「대조군 부재」다.
- ★★ **새 산출물: 「검증 보고서」**(`MC-1` 심의용 리포트와 **별개 파일**).

  1. **각 단계에서 전제한 수치**
  2. **그 전제로 계산된 수치**
  3. **다음 단계로 넘어간 수치**

- ⚠ **「구체적으로 검증 가능한 형태」** — 읽는 사람이 **손계산으로 따라올 수 있어야**

- ⚠⚠ **해설을 붙이지 마라** — §7 이 정한 대로 이 프로그램의 출력은 **정형**이다.

## §3 배터리 역할 — **한 번에 하나. 다만 용량을 갈라 여러 역할은 허용한다**

> *「배터리는 한 번에 하나의 역할만 수행하는 것으로 설계해야 함. 단 용량을 구분하여
> 서로 다른 역할을 수행하는 것은 허용해야 하지 않는가?」*

### 이것이 뜻하는 것 — ★★★ **★V 의 답이다**

**앞 문장은 판정이고, 뒷 문장은 물음표로 끝나지만 설계 지시로 읽는다.**

| | 뜻 |
|---|---|
| **한 번에 하나** | ★ **R51 이 찾은 결함을 「막는다」로 답한 것이다.** 유형 `E` 조합(계통 급전 ↔ 사업자 운전)이 **실행 경로에서 거부돼야 한다** |
| **용량을 갈라 여러 역할** | 한 대의 ESS 를 **용량 몫으로 나누어** 각 몫이 다른 역할을 지는 것은 **허용한다** |

- ⚠⚠ **R51 이 남긴 물음(「거부로 바꾸면 유형 `E` 의 선언 성격과 어긋난다」)은 이
  판정으로 풀린다** — 사용자가 **「설계해야 함」**이라고 적었으므로 **거부가 맞다.**
  ⚠ 그러면 `docs/exclusion-rules.yaml` 의 *「「막는」 규칙이 아니라 「성립하지 않음을
  선언」하는 규칙」* 문면과 **`assert_no_exclusions()` 가 유형 `A` 만 거부한다**는
  조항 근거가 **함께 움직인다** — spec §16.5 개정 대상이다.
- ★★ **「용량 구분」은 새 축이다.** 지금 `ESS` 는 용량 하나에 `mode_weights`(가중치
  혼합)를 갖는다 — **가중치 혼합과 용량 분할은 다른 것이다.** 가중치는 *「같은 용량이
  두 역할을 나눠 진다」*이고 용량 분할은 *「용량 몫이 갈려 각자 한 역할만 진다」*다.
  ⚠ **판정은 뒤쪽을 요구한다** — 앞 문장(「한 번에 하나」)과 모순되지 않으려면
  **몫마다 역할이 하나**여야 한다.
- ⚠ **`mode_weights`(혼합 모드)를 어떻게 할 것인가가 열린다** — 지금 `HYBRID` 는
  같은 용량이 여러 역할을 동시에 지므로 **「한 번에 하나」와 어긋난다.**
  용량 분할로 대체할지, 남길지는 **R52 가 판정해 명시로 적어야 한다.**
- ★ **결론축 영향**: `MC-1` 은 「자가소비 우선」 단일 모드이므로 **거부 규칙만으로는
  안 움직인다.** 용량 분할을 `MC-1` 에 쓰지 않으면 그대로다.

## §6 프로그램 출력과 해설 — **결과 자체로 이해되게. 해설은 별도 해설서로 한 번만**

> *「본 프로그램은 동작 시 AI 없이 계산에 의해서 산출된 값을 도출함. 산출된 결과는
> 산출된 결과 자체로 독자가 이해할 수 있어야 함. 해설은 별도 해설서를 작성하여 작성된
> 결과에 대해서 해설을 하는 방식이 효과적(작성 방법은 1번만 작성하면 다시 작성 불필요,
> 프로그램을 서비스할 때 AI를 활용하지 않을 예정)」*

### 이것이 뜻하는 것 — ★★ **`status-human.md` 7단계의 첫 항목(`FR-1001-AC5`)의 답이다**

- **리포트는 정형 출력이며 해설을 싣지 않는다**(종전 방침 유지 · 양식 0절).
- ★ **그런데 「결과 자체로 독자가 이해할 수 있어야 함」이 함께 요구된다** —

- ⚠⚠ **그러므로 해설서에 「이 사업은 …이다」 같은 판정 문장을 넣지 마라** — 넣으면
  값이 바뀔 때 거짓이 된다(리포트에 해설을 싣지 않는 것과 **같은 이유**다).

  *「리포트만 보고」* 를 지키면 주지 않는 것이 맞고, 「해설서는 도구 사용법이니
  줘도 된다」는 읽기도 가능하다. **R52 는 이것을 대신 정하지 말고 그대로 물어 둔다.**

### 이것이 뜻하는 것 — ★ **`status-human.md` 7단계의 「규칙책 개정」 갈래 하나가 열렸다**

- **규칙책 = `rslt/spec-분산특구-경제성평가.md`** · **설정 = `docs/assumptions.yaml`**
  (가정 대장)로 읽는다.
- **spec 이 든 수치 중 대장에도 있는 것을 spec 에서 뺀다** — 두 곳에 있으면 한쪽만
  고쳐지고, **낡는 쪽이 조용히 거짓이 된다**(이 저장소가 반복해 밟은 형태이며
  §16.1 W-4 「소유를 둘로 갈지 않는다」가 이미 그 원칙이다).
- ⚠⚠ **「예시」와 「전제값」을 가르는 것이 이 일의 어려운 점이다.** spec §13.2.2 의
  손계산 예시(`4,500,000 × 5/25` 등)는 **산식을 설명하는 예시**이고 대장 값이 아니다 —
  **그것까지 빼면 조항이 산식을 잃는다.** ★ **먼저 세고 판단하라**: spec 의 수치를
  전부 훑어 **ⓐ 대장 키와 짝이 되는 것** / **ⓑ 산식 예시** / **ⓒ 조항 자체가 정하는
  상한·기준(예: `NFR-206` 의 500줄)** 으로 갈라 목록을 만든 뒤 **ⓐ 만** 뺀다.
- ⚠ **판본 머리말의 실측 수치는 「그 시점의 기록」이다** — 빼면 이력이 거짓이 된다.
  ★V 계열과 같은 판단이며 **머리말은 대상이 아니다.**
- ⚠ **§16.5 개정 절차를 탄다.** `check_source_rules` 가 spec ↔ 정본 사본 정합을 본다.
