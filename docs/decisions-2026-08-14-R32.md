# R32 결정 — 사용자 몫으로 갈라 두었던 판단을 대신 내린 기록

작성 **2026-08-14 (R32)** · 근거 정본은 **이 파일**이다. `status.md`·spec·코드에
같은 사실을 옮겨 적지 않는다(같은 사실이 두 곳에 있으면 한쪽만 고쳐진다).

> ## ⚠ 이 파일의 판정은 **전부 잠정이다 — 추후 검토에서 바뀔 수 있다**
>
> 사용자가 *「사용자가 판단해야 하는 부분은 합리적으로 판단하고 추후 검토 과정에서
> 변경될 수 있음을 기재하라」* 고 지시했다(2026-08-14). 그래서 R31 이 **「사업 판단」·
> 「자료 공백」으로 갈라 두었던 것**을 여기서 판정하고 착수했다.
>
> **판정마다 세 가지를 함께 적었다**: ① 무엇을 정했나 ② 무엇을 근거로 했나
> ③ **무엇이 오면 바뀌나 · 바뀔 때 고칠 자리는 어디인가.** ③ 이 없으면 잠정
> 판정이 시간이 지나며 확정처럼 읽힌다 — 이 저장소가 「가정값을 등재하되 근거
> 칸을 비우지 않는다」로 다루는 것과 같은 형태다.
>
> **되돌리려면 근거를 먼저 반박해야 한다.** 근거를 읽지 않고 다시 정하면 같은
> 판단을 두 번 하고 두 답이 저장소에 남는다(R31 이 같은 규칙을 세웠다).

## §1 「개별 세대 직접계약」의 정산 대상 — **계통 역송 전력(잉여)·판매 주체 가구**

| | |
|---|---|
| **왜 사용자 몫이었나** | 조항이 *「가구가 구매자와 직접 계약」* 만 적고 정산 대상을 규정하지 않았다. 배타 규칙표가 자가소비와 잉여판매를 **유형 A**(동일 물리량 이중 판매)로 두므로 **둘 중 하나만** 켤 수 있고, 그 선택이 편익을 통째로 바꾼다 |
| **정한 것** | 정산 대상 = **계통 역송 전력(잉여)**. 판매 주체 = **가구**(`Payer.RESIDENT`). 편익 클래스 = `SurplusSale`. 계약단가는 **협상값**이므로 `SettlementInputs` 로 받고 없으면 거부 |
| **근거** | 조항 문면이 *「가구가 구매자와 **직접** 계약」* 이므로 **파는 쪽이 가구**다. 그리고 「직접계약」의 대상이 될 수 있는 전력은 **계량점 밖으로 나가는 것**뿐이다 — 자가소비분은 계약 상대에게 인도되지 않으므로 매매의 대상이 아니다. 사업자를 지불 주체로 두면 관점별 NPV 에서 주민 수익이 통째로 사라지고 **합계는 맞아서 드러나지 않는다**(상계거래에서 이미 같은 판단을 했다) |
| **⚠ 무엇이 오면 바뀌나** | **부지·설비 임대 결합형 계약서.** 가구가 자가소비분까지 계약에 넣는 형태가 실물로 나타나면 정산 대상이 넓어진다 |
| **바뀔 때 고칠 자리** | spec `FR-205-AC1.HouseholdDirect` 아래 주석 · `core/valuestream/settlement.py::_household_direct_contract` **한 곳**. 계약단가는 협상값이라 **대장 개정이 붙지 않는다** |

## §2 관리주체 수수료의 **모수** — 신규(설비 후) 세대 배분 요금

| | |
|---|---|
| **정한 것** | 수수료 = **신규 요금** × `fee.manager_entity`(`Q-14`, **%**). 편익 차감이 아니라 **비용 행**(`core/cba/proforma.py::fee_row`) |
| **근거** | 관리주체가 **해마다 실제로 배분하는 금액**이 신규 요금이므로 수수료의 모수도 그것이다. 「비용으로 낸다」는 편익 차감이 **관점별 NPV 에서 그 지출을 사라지게** 하기 때문이다 — 편익 계정만 줄고 비용 계정에는 한 줄도 남지 않으므로 정부·사회 관점에서 그 비용이 없는 사업이 되고, B/C 분모도 줄어 **같은 사업이 수수료를 편익 차감으로 적으면 유리해진다** |
| **⚠ 무엇이 오면 바뀌나** | **관리규약 표본.** 규약이 기존 요금(설비 전) 기준으로 수수료를 매기면 모수가 바뀐다 — 그 경우 설비를 넣을수록 실효 수수료율이 커진다 |
| **바뀔 때 고칠 자리** | `core/valuestream/settlement.py::_single_contract_via_manager` 의 곱셈 한 줄 + `tests/valuestream/test_settlement_manager_structure.py` 의 손계산 오라클(1,830원) |

## §3 「집합 PPA」의 **지불 주체** — 사업자(집합 대표)

| | |
|---|---|
| **정한 것** | `AggregatedPPA.payer = Payer.OPERATOR`(기본값). 구조별 표(`payer_by_structure`)에 **넣지 않았다** |
| **근거** | 집합 PPA 는 여러 세대·자원을 **묶어** 파는 구조이므로 계약 당사자가 집합 대표다. 기본값과 같은 값을 표에 또 적으면 **소비자가 없는 선언**이 늘고, 이 저장소는 그 형태를 반복해 결함으로 찾았다 |
| **⚠ 무엇이 오면 바뀌나** | **집합 계약서·관리규약**이 정산금의 **세대 직접 배분**을 정하면 `Payer.RESIDENT` 다 |
| **바뀔 때 고칠 자리** | `core/valuestream/aggregated_ppa.py` 의 `payer_by_structure` **한 줄**(신설) |

## §4 `FR-205-AC1` 구조별 분할과 **Phase 귀속** — 판단이 필요하지 않게 만들었다

| | |
|---|---|
| **왜 사용자 몫이었나** | v0.15 가 *「쪼개면 아직 조립되지 않은 구조 셋이 Phase 1 미매핑으로 드러나고, 그것을 Phase 2 로 옮기는 것은 Phase 1 이 약속하는 범위를 줄이는 사업 판단」* 이라 적었다 |
| **정한 것** | **범위를 줄이지 않았다.** 그 셋을 Phase 2 로 옮기는 대신 **조립했다**(§1 결정 · 요금엔진 배선 · 편익 클래스 신설). 그러고 나서 쪼갰다 |
| **결과** | 수용기준 314 → **321**(`AC1` 1건 → 구조 7건 + `FR-401-AC2.AggregatedPPA` 1건). **Phase 1 Must-have 미매핑은 8건 그대로**(전부 Phase 2·3) — 남은 미조립은 이미 Phase 2 인 「VPP 경유」 하나이고 `AC1.VPP` 가 줄 끝 `[Phase 2]` 로 그것을 나른다 |
| **근거** | 사업 판단이 필요했던 이유는 **미조립 셋** 때문이었고, 미조립이 사라지면 그 판단 자체가 사라진다. **순서를 뒤집은 것이 요점이다** — 먼저 쪼개면 판단을 요구받고, 먼저 조립하면 요구받지 않는다 |
| **⚠ 남은 것** | 「VPP 경유」는 `FR-401-AC2.VPPMarket`(Phase 2)이 선행이므로 그 편익이 서기 전에는 조립할 수 없다. **자료가 아니라 순서 문제다** |

## §8 R32 가 이 라운드에 **찾은 것** — 결정과 무관하게 기록한다

### ① 비용 행이 NPV 를 **늘리고** 있었다 (기존 결함)

`core/casegrid/e2e_runner.py` 가 `benefit_rows + cost_rows` 를 `npv()` 에 **그대로**
넘겼다. `CashFlowRow` 는 부호 규약이 없고(「비용도 양수」) `npv()` 는 목록 하나를
**부호 있는 합**으로 보므로, **고정 O&M 이 편익으로 더해졌다.** NPV 가 O&M 현가의
두 배만큼 과대 계상되고 아무 예외도 나지 않는다.

> **R32 가 관리 수수료를 비용 행으로 넣자 「수수료율을 올릴수록 NPV 가 커진다」로
> 드러났다.** 비용 항목이 O&M 둘뿐일 때는 아무도 이 자리를 밟지 않았다 — **새 항목이
> 기존 결함을 밟은 형태**다.

부호를 뒤집을 자리를 **경계 하나**(`net_operating_flows`)로 두었다. `fee_row`·
`fixed_om_row` 를 음수로 바꾸지 않은 이유: 프로포마 표시와 `bcr()` 분모가 함께
뒤집히고, **두 곳에서 뒤집으면 다시 양수가 된다.**

### ② `CaseVariant.overrides()` 를 읽는 배포 코드가 0곳이었다

추상 메서드라 변형 전부가 구현하고 계약 테스트가 반환값을 붙들고 있었는데, 순회는
`baseline` 깃발만 보고 갈랐다. **변형이 둘일 때는 두 기계가 같은 답을 내고 셋째에서
갈린다** — 보조율 15% 를 덮어쓰는 변형이 입력 지원안(30%)과 **똑같은 NPV** 를 내면서
아무 예외도 내지 않는다. 확장점 문서가 *「필요한 것은 파일 하나」* 라고 약속한 것이
**숫자 수준에서는 지켜지지 않는 상태**였다.

### ③ 편익 클래스의 `exclusions()` 선언도 읽는 배포 코드가 0곳이었다

`assert_no_exclusions()` 는 `docs/exclusion-rules.yaml`(정본)만 본다. 그래서
`AggregatedPPA` 의 클래스 선언에서 자가소비 배타를 **지우는 변이가 전건 초록불**이었다.
선언을 강제 경로로 바꾸지 않고(그러면 규칙이 코드로 돌아가 `FR-402-AC4` 가 깨진다)
**선언이 정본과 어긋나지 못하게** 래칫을 세웠다
(`tests/contract/test_exclusion_declaration_matches_table.py`).

> **세 건 다 같은 형태다** — 「선언·계산은 있는데 읽는 쪽이 없다」. R24 가 `DV-10`
> 에서, R31 이 `CaseResult.variants` 에서 만났고 R32 가 **셋을 더 찾았다.** 다음
> 라운드가 기계로 물을 것: **「이 필드·이 메서드를 읽는 배포 코드가 있는가」를
> 열거하는 검사**를 세울 수 있는가.
