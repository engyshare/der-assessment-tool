# R48 결정 — ESS **운영방식 축**을 신설한다 (사용자 판정)

작성 **2026-08-31 (R48 착수)** · 근거 정본은 **이 파일**이다. `status.md`·spec·코드에
같은 사실을 옮겨 적지 않는다(같은 사실이 두 곳에 있으면 한쪽만 고쳐진다).

> ## ★ 이 파일은 **사용자가 직접 내린 판정**이다 — R32 판정과 성격이 다르다
>
> `docs/decisions-2026-08-14-R32.md` 는 *「사용자 몫을 대신 판정하고 잠정으로 적어 둔
> 기록」* 이었다. **이 파일은 그것이 아니다.** 2026-08-31 세션에서 사용자가
> 도메인 판단으로 직접 답한 것이며, **잠정이 아니다.**
>
> 되돌리려면 근거를 먼저 반박해야 한다.

---

## §0 이 판정이 **무엇을 대체하는가**

`docs/evidence/판정요구-이중계상-2026-08-29.md` 가 물은 것 —
*「같은 kWh 가 「잉여판매」와 「기본요금 절감」으로 두 번 화폐가 된다. 어느 쪽을
지울 것인가(甲·乙·丙)」* — **에 대한 답이며, 그 세 갈래를 전부 대체한다.**

**갈래 셋은 채택되지 않는다.** 사용자 판정은 *「편익을 지우는」* 것이 아니라
*「ESS 가 어떻게 운영되는지를 먼저 규정하고, 편익을 그 운영방식에서 산정한다」* 이다.

> ### ⚠ 그러면 이중계상은 **규칙이 아니라 구조가** 막는다
>
> 종전 물음은 *「배타 규칙표에 `SurplusSale × PeakShaving` 쌍을 넣을 것인가」* 였다.
> 운영방식을 규정하면 **그 쌍을 넣을 필요가 없다** — 자가 부하로 간 kWh 와 계통으로
> 나간 kWh 가 **수량 단계에서 갈리므로** 같은 kWh 가 두 항목에 들어갈 수 없다.
> **규칙으로 막는 것보다 강하다.**
>
> ⚠ 다만 **배타 규칙은 여전히 필요하다** — §2 가 정하는 「운전 주체」 축에서다.

## §1 이 사업의 ESS 는 **태양광 연계**다 — PV 잉여로 충전, 저녁 방전

| | |
|---|---|
| **왜 판정이 필요했나** | `core/casegrid/e2e_runner.py:470` 이 `operating_mode=ESSOperatingMode.PEAK_SHAVING` 을 **코드에 하드코딩**하고 있었다. 그 모드의 충전창은 **01~06시**이므로 배터리가 **심야에 계통에서 사서** 낮에 계통으로 파는 운전을 하고 있었다 — 태양광 연계 ESS 의 운전이 아니다 |
| **정한 것** | 이 사업의 ESS 는 **태양광 연계**다. **태양광 전력이 남을 때(낮) 충전하고 저녁에 방전**한다 |
| **근거** | 사용자 판정(2026-08-31): *「배터리는 사용 용도에 따라 운전 방식이 다를 수 있음. 계통에서 충전할 수도 있지만, **태양광 연계 ESS는 낮시간에 태양광 전력이 남을 때 충전해야 함**」* |
| **⚠ 무엇이 오면 바뀌나** | 사업 구성이 PV 비연계 독립 ESS 로 바뀌면. 그때는 §2 의 다른 운전 방식이 선다 |

### ⚠⚠ 그런데 **「충전원」을 규정하는 축이 저장소에 없다**

`core/der/ess.py` 의 `_MODE_WINDOWS` 는 **시간창만** 정한다:

```
자가소비 우선 : 충전 (10,11,12,13,14,15)  방전 (18,19,20,21)
TOU 차익거래  : 충전 (1,2,3,4,5,6)        방전 (18,19,20,21)
피크 저감     : 충전 (1,2,3,4,5,6)        방전 (13,14,15,16)
백업 예비     : 충전 (1,2,3,4,5,6)        방전 (18,19,20,21)
```

**어디서 충전하는가가 어디에도 없다.** 시간대가 우연히 PV 발전시간과 겹치면 PV 로
충전되는 것처럼 보일 뿐, **PV 잉여 범위 안에서만 충전하라는 제약이 없다.**

**정한 것** — **충전원(`charge_source`) 축을 신설한다.** 최소 두 값:

| 값 | 뜻 | 제약 |
|---|---|---|
| `PV_SURPLUS` | 태양광 잉여로만 충전 | 매 스텝 충전량 ≤ **그 스텝의 PV 잉여**. 넘으면 **거부하고 원인을 보고**한다(잘라내지 않는다 — `ess.py` 독스트링 「스스로 지키는 것 셋」 ①) |
| `GRID` | 계통에서 충전 | 종전 동작. 전력 구매 비용이 붙는다 |

⚠ **`PV_SURPLUS` 는 「PV 가 있어야」 성립한다.** PV 없는 구성에서 이 값을 주면
**거부한다** — 조용히 0 충전으로 두면 편익이 사라진 채 초록불이 된다.

## §2 ★★ **운전 주체**가 최상위 축이다 — 사용자 운전 ↔ 계통운영자 급전

이것이 이번 판정의 **핵심**이며, 배타 규칙의 진짜 근거다.

| | |
|---|---|
| **왜 판정이 필요했나** | 착수 시점의 오케스트레이터는 CP·NWAs 를 *「운전 방식과 **직교**하는 축(등록하면 어느 모드 위에든 얹힌다)」* 으로 가정하고 사용자에게 확인을 요청했다. **그 가정이 틀렸다** |
| **정한 것** | **CP·NWAs 는 직교 축이 아니라 배타 축이다.** 그 구조에서는 **방전 시점을 사용자가 정할 수 없으므로**, 자가소비·피크저감이 **성립하지 않는다** |
| **근거** | 사용자 판정(2026-08-31): *「**CP를 받는 구조이면, 사용자가 원하는 시간에 방전할 수 없음. 사용자의 전기사용량에 영향이 없음(자가 소비가 아님)**. NWAs도 동일함. **배전선로의 상황에 맞게 동작**하며 자가소비의 개념이 아님」* |

### 축의 모양

```
운전 주체 ─┬─ 사용자 운전 : 방전 시점을 사업자가 정한다
           │                 → 자가소비 절감 · 피크 저감 · (잉여) 판매 · TOU 차익
           │
           └─ 계통 급전   : 방전 시점을 계통운영자가 정한다
                             → CP(용량정산금) · NWAs(계통 기여 보상)
                             ⚠ 자가소비·피크저감이 성립하지 않는다
```

★ **배타 규칙은 이 축에서 선다** — 「`SurplusSale` × `PeakShaving`」이 아니라
**「계통 급전 편익(CP·NWAs) × 사용자 운전 편익(SelfConsumption·PeakShaving)」**이다.
`docs/exclusion-rules.yaml` 의 **유형 A**(동일 물리량 이중 계상)와 성격이 다르므로
**유형을 새로 세울지 판정이 필요하다**(같은 kWh 를 두 번 파는 것이 아니라, **동시에
성립할 수 없는 운전**이다). ⚠ 이것은 **spec §16.5 안건**이다.

### `e2e_runner.py:255` 주석을 고쳐야 한다

지금 *「내장 편익 둘(`SurplusSale`·`PeakShaving`)은 배타 쌍이 아니다」* 라고 적혀 있다.
그 진술 자체는 이 판정 뒤에도 **참일 수 있다**(둘 다 사용자 운전이다). 그러나
**그 주석이 이중계상을 정당화하는 근거로 인용돼 왔으므로**, 무엇이 실제 배타 축인지를
가리키도록 고친다.

## §3 운전 방식은 **사용자가 고를 수 있어야** 한다

| | |
|---|---|
| **정한 것** | 운전 방식을 **시나리오/모델 파라미터로 노출**한다. 코드 하드코딩(`e2e_runner.py:470`)을 걷어낸다 |
| **근거** | 사용자 판정: *「**운전 모드 설정이 가능해야 함**」*. 그리고 spec `FR-105-AC2` 가 이미 *「새 운전 방법 추가 시 코어 엔진 수정 0줄」* 을 요구한다 — 러너가 값을 박는 것은 그 조항의 취지에 어긋난다 |

## §4 편익은 **운영방식이 정한다** — 산정식 표

| 운전 방식 | 충전원 | 방전 대상 | 편익 | 지금 상태 |
|---|---|---|---|---|
| **자가소비 우선** | PV 잉여 | 자가 부하 | 회피 전력요금 | 시간창만 있음 · 충전원 미규정 |
| **피크 저감** | (규정 필요) | 자가 부하 | **자가 피크 절감 kW** × 기본요금 × 12 | ❌ **부하를 안 본다** (아래 ⚠) |
| **TOU 차익거래** | 계통(경부하) | 계통(피크) | **충·방전 요금차** | ⚠ 함수는 있는데 **미배선** (아래 ⚠⚠) |
| **계통 방전 (NWAs)** | — | 계통 | 계통 기여 수준 보상 | ❌ **개념 없음** — 신설 |
| **준중앙급전 등록 (CP)** | — | 계통 | 용량정산금 | ❌ **개념 없음** — 신설 |
| **백업 예비** | — | — | 정전 회피(`Resilience`) | Phase 3 — 손대지 않는다 |

**근거** — 사용자 판정: *「편익은 운영방식에 따라 달라질 수 있음. **기본요금 절감
목적으로 운영되는 ESS는 자가피크전력을 절감한 것만큼 편익이 발생해야 함.** 계통으로
방전하는 경우에는 계통운영자로부터 계통에 기여하는 수준에 해당하는 보상을 받을 수
있으며(NWAs), 단순 차익거래를 하는 경우에는 **충방전요금차이만큼**을 수익으로 올릴 수
있음. 따라서 ESS가 어떻게 운영하는지를 규정하고, 운영 방식에 따라 편익을 산정해야 함」*

### ⚠ 피크 저감이 **자가 부하를 보지 않는다** — 고쳐야 한다

```python
# core/der/ess.py  reducible_peak_kw()
return min(self.power_kw, self.usable_capacity_kwh(year=year) / window_hours)
```

**부하가 인자로 들어오지 않는다.** 그래서 방전 전량이 계통으로 나가도 2.00kW 가
계상됐다 — 이것이 「이중계상」으로 보였던 것의 절반이다.
**정한 것** — 피크 저감 편익은 **자가 부하와 겹치는 방전분**에서만 난다.
**부하 자료가 없으면 0 이다**(§5 가 그 자료를 세운다).

### ⚠⚠ 차익거래 편익 함수가 **호출자 0곳**이다

`ESS.tou_arbitrage_benefit()`(= `방전 kWh × 피크단가 − 충전 kWh × 경부하단가`,
사용자가 말한 「충방전요금차이」와 **같은 산식**)이 구현돼 있는데 **호출자가
`tests/der/test_ess.py::test_rc_ess_b1_tou_arbitrage_benefit` 하나뿐**이다(실측).
그리고 `ESS.value_streams()` 는 **TOU 차익거래 모드를 `SelfConsumption` 으로 매핑**한다
— 계통에 파는 운전인데 자가소비 편익이 붙는다. **둘 다 결함이다.**

### ⚠⚠⚠ 계통 방전분이 **태양광의 잉여판매에 얹혀 있다**

`ESS.value_streams()` 는 `SurplusSale` 을 **선언하지 않는다.** 그런데 `SurplusSale` 은
**시스템 총 역송량**으로 계산된다 — 대표일 18.80kWh = PV 10.80 + ESS 방전 8.00.
그래서 **ESS 가 내보낸 8.00kWh 의 값 321,200원/년이 태양광 행에 얹힌다.**

**이것이 「이중계상」의 진짜 정체다** — 두 번 센 것이 아니라, **계통 방전분을 받을
편익 항목이 없어서 남의 항목에 얹힌 것**이다. §4 표의 NWAs·CP 가 그 자리를 만든다.

## §5 가구 부하 — **월 300kWh 기준 · 추가 기기 비례 증가**

| | |
|---|---|
| **왜 판정이 필요했나** | 이 실행에 **가구 부하 시계열이 없다**(`Q-3` 지자체 회신 대기 · `status-human.md`). 자료가 없어서 피크 저감이 부하를 못 보는 결함(§4 ⚠)이 드러나지 않았다 |
| **정한 것** | **일반 가정 = 월 300kWh** 수준으로 부하 자료를 **작성한다**. **히트펌프 등 추가 전력사용기기가 있으면 그에 비례해 사용량이 증가**하는 형태여야 한다 |
| **근거** | 사용자 판정(2026-08-31) |
| **⚠ 이것은 가정값이다** | `Q-3` 실측 회신이 오면 **교체된다.** 그러므로 **`docs/assumptions.yaml` 에 근거 칸을 채워 등재**하고, 리포트 붙임 6(전 가정 목록)에 나오게 한다. ⚠ **골든에 수만 박고 대장에 안 적으면 그 순간 출처 없는 수가 된다** |

⚠ **월 300kWh 는 연 3,600kWh 다.** 시간별 형상(계절·주야)은 이 판정이 정하지 않았다 —
**작성자가 정하고 그 근거를 대장의 근거 칸에 적는다.**

## §6 NWAs·CP 의 **제도 상태** — 둘 다 「제도 필요」로 표시한다

| 편익 | 현행 제도인가 | 무엇이 없는가 | 리포트 표시 |
|---|---|---|---|
| **NWAs** | **아니다 — 현재 설계 중** | 제도 자체 | **제도 필요** |
| **CP** | **현행 제도다** | ⚠ **분산특구 내 ESS 에 대한 CP 산정 기준이 부재.** CP 는 **등록 발전기 기준**으로 설정돼 있다 | **제도 보완 필요** |

**근거** — 사용자 판정: *「NWAs는 현행이 아님. 현재 설계중. CP는 현행 제도임.
**둘 다 필요한 제도로 생각함.** 그러나 **분산특구 내 ESS에 대해서 CP 산정 기준이 부재.
CP는 등록 발전기 기준으로 설정되어 있음**」*

> ### ★ 이 판정이 §7(정책 경고 문구)과 만난다
>
> 사용자는 별도로 *「사업성이 떨어지는 사업에 대해서는 정부가 제도를 만들어서
> 사업성을 보조해야 함. **보고서에는 제도가 바뀌어야 한다는 문구를 쓰도록 수정**」*
> 을 지시했다. **NWAs·CP 가 바로 그 문구가 붙는 편익**이다 — 두 지시가 여기서 만난다.
>
> ⚠ **CP 는 「제도가 없다」가 아니라 「이 사업에 적용할 산정 기준이 없다」이다.**
> 문구를 뭉뚱그리지 마라 — 둘은 심의회에서 다른 답을 요구한다.

## §7 정책 가정 편익의 **경고 문구** — `policy_warnings()` 를 `DER` 계약에 올린다

| | |
|---|---|
| **왜 판정이 필요했나** | `FR-404-AC1` 이 요구하는 표시를 **리포트가 아예 내지 않는다** — `core/report/` 에 호출자가 **0곳**이다. 그리고 `policy_warnings()` 는 지금 **`EV_V2G` 에만** 있다 |

## §11 ★ **운전 규칙** — 잉여는 ESS 로, 저녁·피크에 방전, **모자라면 용량만큼만 동작**

> ⚠ **이 절은 라운드 도중(2026-08-31 R48 실행 중)에 사용자가 추가로 내린 판정이다.**
> §1 이 *「태양광 전력이 남을 때 충전」* 만 정하고 **어떤 시각에 얼마나**를 정하지
> 않아서 구현이 막혔고, 그 물음에 사용자가 답했다. **잠정이 아니다.**

| | |
|---|---|
| **왜 판정이 필요했나** | §1 을 구현하니 **기준 구성이 성립하지 않았다.** 실측 — PV 3kW·이용률 15% 의 하루 발전은 **10.80kWh** 이고 ESS 10kWh·SOC 10~90%·365사이클의 하루 충전 필요량은 **8.89kWh** 인데, 자가소비 우선 모드의 충전창(10~15시)에 드는 발전은 **6.50kWh** 뿐이다. §1 의 「넘으면 거부」를 그대로 걸자 `pytest` **160건**이 같은 예외 하나로 빨간불이 됐다 |
| **정한 것** | **자가소비량을 초과하는 태양광 발전량(잉여)은 ESS 로 충전하고, 저녁 시간(또는 피크 시간)에 방전한다. 설비 용량이 부족하면 설비 용량만큼 동작한다** |
| **근거** | 사용자 판정(2026-08-31, 라운드 실행 중): *「일반적으로는 자가소비량을 초과하는 태양광발전량은 ESS 충전되고, 저녁 시간(또는 피크시간)에 방전하는 것이 일반적임. 만약 설비 용량이 부족한 경우에는 **설비 용량만큼 동작**해야 함」* |

### 이 규칙이 §1 의 「거부」와 만나는 자리 — **거부는 남되 자리가 다르다**

- **충전 시각은 고정 창이 아니다.** `_MODE_WINDOWS` 의 `(10,11,12,13,14,15)` 는
  **충전원을 규정하기 전에 만들어진 관례**이며 사용자 규칙은 시각을 지정하지 않았다.
  `PV_SURPLUS` 에서 충전 시각은 **「잉여 > 0 인 모든 시각」**(방전창 제외)이다.
- **시각별 충전량 = min( 그 시각의 잉여, 정격출력이 받을 수 있는 양, 남은 저장 여유 )**.
  잉여가 모자라면 **덜 충전되고**, ESS 가 다 못 받으면 **남은 잉여는 계통으로 나간다.**
  양쪽이 대칭이다.
- ⚠ **이것은 「잘라내기」가 아니다.** `ess.py` 독스트링 「스스로 지키는 것 셋」 ① 이
  금지한 것은 *「한도를 넘는 **계획**을 조용히 잘라 남은 값으로 수지를 닫는 것」* 이다.
  여기서는 **애초에 넘는 계획을 세우지 않는다** — 못 받은 잉여는 잉여판매로 남고,
  덜 충전된 만큼 방전이 주는 것은 **실제로 그만큼만 저장했기 때문**이다.
- ⚠⚠ **남는 거부** — `PV_SURPLUS` 인데 잉여 시계열이 **없거나 전부 0** 이면 거부한다(§1).
  없어지는 것은 **「시각별 충전량 > 잉여」 하나뿐**이고, 그것은 이제 구조적으로
  일어나지 않는다.

### 그래서 `cycles_per_year` 는 `PV_SURPLUS` 에서 **입력이 아니라 결과**다

연 방전량이 `가용량 × 사이클수(365)` 로 **가정에서** 나오고 있었는데, **365 는 계통에서
언제든 살 수 있음을 전제한 값**이다. 태양광 연계에서는 성립하지 않는다 — 연 충전량은
**잉여가 정하고** `cycles_per_year` 는 **상한으로만** 쓴다.

⚠ **「얼마나 못 채웠는가」가 보여야 한다.** 실제 연 충전량·실제 사이클을 밖에서 읽을 수
있게 둔다 — 그러지 않으면 *「365 사이클로 사 놓고 그만큼 돌지 않았다」* 가 아무 데도
안 남는다. **그것은 이 사업이 답해야 하는 물음이지 감출 일이 아니다.**
