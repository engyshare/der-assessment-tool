# spec 작성 원칙

> 본 프로젝트의 SRS v0.1 → v0.2 검토에서 실제로 발견된 문제를 원칙으로 정리한 것이다.
> 새 spec을 쓰거나 기존 spec을 개정할 때 이 문서를 먼저 확인한다.

---

## 1. 우선순위와 시점은 별개의 축이다

가장 많은 혼선을 일으킨 지점이다. v0.2에서 Must-have 10여 건이 Phase 표에 배정되지 않은 채 남았고, 그 상태로 작업 분해에 들어가면 그대로 누락된다.

### 1.1 우선순위 = 중요도 (무엇이 없으면 안 되는가)

| 등급 | 정의 | 판별 기준 |
|---|---|---|
| **Must-have** | 이것이 없으면 **시스템이 목적을 달성하지 못한다.** 원 요구사항에 직접 대응하거나, 다른 Must-have가 동작하기 위한 전제 | 빼면 제품이 성립하는가? → 성립 안 하면 Must |
| **Should-have** | 없어도 시스템은 성립하나 **실용성이 크게 떨어진다** | 빼면 불편한가, 못 쓰는가? → 불편하면 Should |
| **Nice-to-have** | 있으면 좋다. 우선순위 경쟁에서 언제든 밀릴 수 있다 | 빼도 아무도 불평하지 않으면 Nice |

**Must-have는 "코드 작성 시 반드시 반영"이 맞다. 단 그것만으로는 부족하다.** "반드시"는 대상을 정할 뿐 시점을 정하지 않기 때문이다.

### 1.2 Phase = 시점 (언제 만드는가)

Phase는 **일정과 의존관계**로 결정된다. 우선순위와 독립이다.

- Must-have가 Phase 2일 수 있다 — 중요하지만 Phase 1 기반 위에서만 만들 수 있는 경우
- Should-have가 Phase 1일 수 있다 — 나중에 넣으면 구조를 뜯어야 하는 경우

### 1.3 두 축을 잇는 강제 규칙

> **원칙 1-A.** 모든 요구사항은 **우선순위와 Phase를 둘 다** 가진다. 하나라도 없으면 미완성 요구사항이다.
>
> **원칙 1-B.** **Must-have는 예외 없이 어떤 Phase에든 배정되어야 한다.** 배정되지 않은 Must-have는 "중요하다고 써 놓고 만들 계획은 없는 것"이며, 이는 spec의 결함이다.
>
> **원칙 1-C.** 어떤 Phase의 완료조건(DoD)은 **그 Phase까지 배정된 요구사항만으로 달성 가능**해야 한다. Phase 2 기능을 Phase 1 완료조건에 넣으면 그 Phase는 영원히 끝나지 않는다.
>
> **원칙 1-D.** Must-have를 Phase 2 이후로 미룰 때는 **Phase 1 완료 시점에 무엇을 못 하는지** 명시한다. 조용히 미루면 Phase 1을 "완료"로 선언한 뒤에야 빈 곳을 발견한다.

### 1.4 검증 방법

부록의 추적 매트릭스에 **Phase 열을 반드시 둔다.** 그러면 다음이 눈으로 검사된다.

```
Must-have 총 N건 = Phase 1 배정 + Phase 2 배정 + Phase 3 배정
                   (좌우가 안 맞으면 미배정 항목이 있다)
```

## 2. 요구사항 문장 작성

**원칙 2-1 (검증 가능성).** 모든 요구사항은 **참/거짓을 판정할 수 있는 수용기준**을 가진다. "사용하기 쉬워야 한다"는 요구사항이 아니다. "비개발자가 튜토리얼 30분 이내에 첫 결과를 산출한다 / 측정: 사용자 5명 태스크 테스트"가 요구사항이다.

**원칙 2-2 (측정 방법 명기).** NFR은 수치와 함께 **어떻게 측정하는지**를 반드시 쓴다. 측정 방법이 없는 수치는 나중에 아무도 확인하지 않는다.

**원칙 2-3 (근거 있는 수치만).** spec에 등장하는 모든 임계값은 근거가 있어야 한다.
- 좋음: "파일당 500줄 상한 — 근거: 참조 구현의 1,830줄 단일 파일 유지보수 실패 사례"
- 나쁨: "3단계 이내로 추적 가능" — 왜 3인지, 무엇이 1단계인지 정의 없음

> **근거를 못 대는 수치는 쓰지 말고, 그 수치가 대신하려던 목적을 직접 쓴다.**
> "3단계 이내 추적" → "결과에 영향을 미친 주요 인자를 영향도 순으로 제시하고, 각 인자의 값·출처·산식을 함께 확인할 수 있다"

**원칙 2-4 (Rationale).** 원 요구사항에서 직접 나온 항목은 **원문을 인용**해 둔다. 나중에 "이건 왜 넣었지"를 묻지 않게 된다.

**원칙 2-5 (사용자 언어).** 수용기준은 개발자가 아니라 **요구한 사람이 읽고 판정할 수 있는 언어**로 쓴다. 클릭 횟수·API 응답 구조가 아니라 "무엇을 알 수 있게 되는가"로 쓴다.

## 3. 정합성 — spec 안에서 서로 어긋나지 않기

v0.2에서 실제로 발견된 유형이다. 모두 기계적으로 검사 가능하다.

### 3.1 교차 참조

> **원칙 3-A.** 요구사항 번호를 재배치하면 **본문의 모든 참조를 함께 갱신**한다.

v0.2 사례: IncentiveScheme이 FR-501 → FR-604로 이동했는데 본문 참조는 FR-603(다른 요구사항)을 가리킨 채 남았다. 번호 변경 시 전문 검색으로 확인한다.

### 3.2 수치 간 산술

> **원칙 3-B.** 서로 계산 관계에 있는 수치는 **직접 산술 검산**한다.

v0.2 사례:
```
NFR-001  단일 케이스 ≤ 5초 (1 vCPU)
NFR-002  100 케이스 ≤ 120초 (병렬)
→ 1 vCPU에서 병렬 이득 없음 → 100 × 5초 = 500초 ≫ 120초. 모순.
```
성능·용량·기간 수치는 반드시 곱셈·나눗셈으로 맞춰 본다. "주의가 필요하다"는 문장을 덧붙이는 것으로는 모순이 해소되지 않는다.

### 3.3 데이터 소유권

> **원칙 3-C.** 하나의 데이터는 **하나의 엔티티만 소유**한다. 두 곳이 같은 것을 가리키면 어느 쪽이 우선인지 정해야 하고, 그 판단을 코드 작성자에게 떠넘기면 안 된다.

v0.2 사례: 규제 프로파일을 AssumptionSet과 Scenario가 모두 참조 → "동일 전제 보장"이 깨질 수 있음.

작성 시 각 개념 엔티티에 대해 **"이 필드의 단일 소유자는 누구인가"** 를 한 번씩 확인한다.

### 3.4 범위 선언 vs 본문

> **원칙 3-D.** In Scope에 넣은 항목은 본문에 요구사항이 있어야 하고, Out of Scope에 넣은 항목은 본문에 요구사항이 없어야 한다.

### 3.5 정합성 점검 목록

개정 때마다 다음을 확인한다.

- [ ] 본문의 모든 `FR-xxx` / `NFR-xxx` 참조가 실제 존재하고 의도한 대상을 가리키는가
- [ ] Must-have 중 Phase 미배정이 0건인가
- [ ] 각 Phase의 DoD가 그 Phase 범위 안에서 달성 가능한가
- [ ] 성능·용량 수치가 서로 곱셈으로 맞는가
- [ ] 개념 엔티티의 각 필드에 소유자가 하나인가
- [ ] In/Out of Scope와 본문 요구사항이 일치하는가
- [ ] 성공기준이 어느 Phase에서 달성되는지 명시되었는가

## 4. 문제 정의는 사실이어야 한다

**원칙 4-1.** 현행 방식의 문제를 과장하지 않는다. 과장된 문제 정의는 **잘못된 해결책을 설계하게 만든다.**

v0.1 사례: "엑셀은 재현 불가"라고 썼으나 사실이 아니다. 엑셀은 셀 수식이 열려 있어 재현 가능하다. 이 오진 위에서 "재현성 확보"를 최우선 가치로 삼았고, 정작 진짜 한계인 **모델 다양성**과 **조합 탐색**은 부차적으로 다뤄졌다.

**원칙 4-2.** 문제를 재정의하면 **목표·성공기준·Phase 계획까지 함께 재정렬**한다. §1만 고치고 나머지를 두면 문서가 두 개의 논리를 동시에 갖게 된다.

**원칙 4-3.** 현행 방식이 **잘하는 것도 명시**한다. 그래야 새 시스템의 범위를 올바르게 좁힐 수 있다. (v0.2에서 "단건 정밀 검산은 엑셀로 계속" → 수식 포함 XLSX 내보내기 요구사항으로 연결된 것이 좋은 예)

**원칙 4-4.** 문제(P-n) → 해소 수단(FR) → 검증(성공기준/KPI)의 **3열 추적표**를 만든다. 어느 문제에도 대응하지 않는 요구사항은 범위 초과를 의심하고, 해소 수단이 없는 문제는 미완성이다.

## 5. 참조 구현·외부 설계의 취급

**원칙 5-1 (판정 없는 차용 금지).** "○○를 차용한다"고 쓰기 전에 항목별로 판정한다.

두 축으로 평가하고 **둘 다 충족할 때만 채택**한다.

| 축 | 질문 |
|---|---|
| **비자명성** | 유능한 설계자가 백지에서 독립적으로 도달하기 어려운 결정인가 |
| **적합성** | 우리 문제나 원 요구사항을 직접 해결하는가 |

- 비자명성 없음 → 차용이 아니라 **독립 도달**이다. "차용"이라 쓰면 근거 없는 권위 부여이자, 원 요구자가 이미 지정한 방향을 남의 공으로 돌리는 것이다
- 적합성 없음 → 불필요한 복잡도다

**원칙 5-2 (배제 항목도 기록).** 참조 구현의 **결함도 함께 조사**하고, 각각을 방어하는 NFR로 전환한다. "무엇을 따라하지 않을 것인가"가 "무엇을 따라할 것인가"만큼 중요하다.

**원칙 5-3 (근거 검증 가능하게).** 참조 코드를 인용할 때 **파일 경로와 함수·라인을 명시**한다. 검토자가 직접 열어 확인할 수 있어야 한다. 경로는 실제 경로여야 한다.

**원칙 5-4 (라이선스 판단 명시).** 코드를 쓰는지 설계 아이디어만 쓰는지 분명히 하고, 그에 따른 의무를 명시한다.

## 6. 미확정 사항의 취급

**원칙 6-1.** 모르는 것을 아는 척하지 않는다. Open Questions에 **영향도·확보처·우선순위**와 함께 남긴다.

**원칙 6-2 (입력 문제와 설계 문제 구분).** 값이 미확정인 것과 설계가 미결정인 것은 다르다.
- **입력 미확정** → 개발 착수를 막지 않는다. 시스템이 `미확인` 플래그로 수용하도록 설계한다
- **설계 미결정** → 착수를 막는다. Phase 시작 전 결정해야 한다

**원칙 6-3 (산출물은 입력이 아니다).** 시스템이 계산해 낼 값을 "선결 확보 필요"로 분류하지 않았는지 확인한다.

v0.1 사례: "보조율 미확정"을 최우선 선결과제로 두었으나, 보조율은 이 시스템의 **산출물**이다. 확보해야 할 것은 보조율이 아니라 보조율을 도출할 전제(설비단가·성능·요금)였다.

**원칙 6-4 (기술 불확실성은 검증 계획과 함께).** "될지 모르겠다"로 끝내지 않고 **언제 어떻게 확인할지**를 함께 쓴다.

## 7. Phase 계획

**원칙 7-1 (Phase 1은 검증 가능한 최소 단위).** "동작하는 얇은 수직 슬라이스"여야 한다. 계층별로 잘라 "Phase 1은 도메인만"으로 하면 Phase 1 종료 시 아무것도 보여줄 수 없다.

**원칙 7-2 (규모 검산).** Phase 산출물 개수와 기간을 곱셈으로 확인한다. 18개 산출물 / 8주 = 항목당 3일이며, 여기에 웹 UI·인증·배포·CI가 포함되면 비현실적이다. 규모가 안 맞으면 **기간을 늘리거나 항목을 줄이거나 둘 중 하나**를 하고, 조정 결과를 문서에 반영한다.

**원칙 7-3 (DoD는 확인 가능한 행위로).** "구현 완료"가 아니라 "누가 무엇을 해서 무엇을 확인한다"로 쓴다.

**원칙 7-4 (성공기준에 Phase 표기).** 성공기준마다 어느 Phase에서 달성되는지 쓴다. 그러지 않으면 Phase 1 완료조건과 충돌한다.

## 8. 문서 관리

**원칙 8-1 (변경 요약).** 개정 시 frontmatter 아래에 **무엇을 왜 바꿨는지** 요약한다.

**원칙 8-2 (구버전 정리).** 같은 이름의 구버전 파일을 여러 위치에 남기지 않는다. 대체되었으면 삭제하거나 `archive/`로 옮긴다.

**원칙 8-3 (의견 반영 흔적).** 검토 의견을 반영할 때 **원 의견을 인용**하고 어떻게 반영했는지 쓴다. 반영하지 않기로 한 것도 사유와 함께 남긴다.

**원칙 8-4 (도메인 원칙 분리).** 구현과 무관하게 성립하는 도메인 원칙은 **별도 문서로 분리**하고 spec에서 참조한다. spec에 섞으면 도메인 원칙이 특정 구현에 종속된 것처럼 보이고, 도구를 바꿀 때 함께 버려진다.

## 9. 하지 말아야 할 것

| 금지 | 이유 |
|---|---|
| 근거 없는 임계값 (`3단계`, `5개`) | 검증 불가, 나중에 아무도 지키지 않음 |
| 판정 없는 "○○ 차용" | 근거 없는 권위 부여 |
| 측정 방법 없는 NFR | 확인되지 않음 |
| Phase 미배정 Must-have | 조용히 누락됨 |
| 같은 데이터의 이중 소유 | 판단을 구현자에게 전가 |
| 문제 과장 | 잘못된 해결책 설계 |
| 산출물을 선결과제로 분류 | 불필요한 대기 |
| "주의가 필요하다"로 모순 봉합 | 모순은 그대로 남음 |
| 요구사항 번호 재배치 후 참조 미갱신 | 오독 유발 |
| 개정 시 §1만 고치고 나머지 방치 | 문서 안에 두 논리 공존 |

## 10. 개정 완료 전 최종 확인

- [ ] Must-have 전건이 Phase에 배정되었는가
- [ ] 각 Phase DoD가 그 Phase 범위로 달성 가능한가
